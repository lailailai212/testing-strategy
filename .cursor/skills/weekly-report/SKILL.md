# Weekly Report

生成可贴飞书文档/群的**测试周报**，版式与用户现用格式一致。

## 输出版式（强制，勿改标题）

```markdown
本周工作

1. …
2. …
3. …

下周计划

1. …
2. …
3. …

需要协调与帮助

暂无。
```

有协调项时，「需要协调与帮助」下用编号或短句列出；**无则写「暂无。」**（带句号）。

### 本周工作 / 下周计划 写法

- 一级用 `1. 2. 3.`，按**工作包**聚合（同一 Sprint / 同一回归包 / 同一主题），不要一条 Story 一行流水账。
- 进度与状态跟在标题后，风格与现网一致，例如：
  - `进度100%`
  - `进度60%`
  - 阶段完成写 `Done`（如：测试点设计 Done · 用例设计 Done · 用例评审 Done）
  - 飞书侧验收未完写 `待验收`
- 子项用 `-` 列表；需求/主题用 `【…】` 标签（如 `【体验优化P2】`、`【自注册】002-02`）。
- Sprint 写清 ID：`OBIS-YYYYMMDD-YYYYMMDD`。
- **下周计划**以**日历与 Sprint 边界**为准，不要只看飞书当前节点名：
  - 若本周写报日 ≥ 当前 Sprint 结束日（ID 后缀日期，如 `…-20260807`），或个人排期 `end_time` 已到本周结束 → **默认本 Sprint 测试包收口**，下周写**下一 Sprint**（如 `OBIS-20260810-20260821`）的设计/排期/提测准备，**禁止**再写「继续本 Sprint 测试执行」。
  - 仅当用户明确说「下周还要补测/返工本 Sprint」时，才把旧 Sprint 放进下周。
  - 写下周前**必须**用 MQL 查下一 Sprint 的 Story（`WHERE Sprint = 'OBIS-…'`），有结果则按新 Sprint 归纳；查不到再问用户。
  - 「承接本周未完」只适用于**未跨 Sprint 边界**的未完项（同 Sprint 内阶段切换，如设计→执行）。
- 误判警示：`list_todo` / 节点仍为「测试」≠ 下周还要继续测——节点滞后很常见，**排期结束日与 Sprint ID 优先于节点名**。

### 样例（语气与粒度）

```markdown
本周工作

1. 聚焦OBIS-20260706-20260724收尾测试，进度100%
  - 【自注册】002-02 Demo编排预置与数据：待验收
  - 【自注册】002-01 Demo编排数据：待验收
  - 权限：仅产品/资源管理员可创建模块：待验收
2. OBIS-20260727-20260807：测试点设计 Done · 用例设计 Done · 用例评审 Done
  - 【体验优化P2】详情补充（Account/Member 等一致性）
  - 【体验优化P2】Member 功能统一
  - 【体验优化P2】Audit 统一
3. 回归用例整理（Product Asset 模块），进度60%

下周计划

1. 开发提测评审
2. OBIS-20260727-20260807 进入测试用例执行
  - 【体验优化P2】详情补充 / Member / Audit
3. 继续回归用例整理（Product Asset 模块）

需要协调与帮助

暂无。
```

## 输入

| 项 | 说明 |
|----|------|
| 统计周 | 默认「上一个自然周」或用户指定起止日期 |
| `project_key` | 默认 `obis`（或用户指定） |
| 焦点人 | 默认当前用户 / 用户点名的测试同学（用于 `list_todo`） |
| 补充事实 | 用户口述的进度%、待验收、回归整理等（飞书没有的本地工作） |

## 数据源（只用不完整以外的）

### 主源：飞书项目 MCP（`user-FeishuProjectMcp`）

按需调用（先 `GetMcpTools` 再调）：

1. `list_todo` — 我的待办/已办（需求、任务、缺陷），圈定本周相关项  
2. `search_by_mql` — 按 Sprint / 状态 / 类型补全 Story、Bug 列表  
3. `get_workitem_brief` — 单条补名称、状态、Sprint、优先级  
4. （可选）`list_schedule` — 本周排期，仅作「做了哪些包」的线索，不写进工时流水

拉取后**归纳成工作包**，再写成编号段；禁止把 MCP 原始字段名直接贴进周报。

### 辅源（可选）

- `docs/sprints/features-registry.json` + 对应 feature `META.md` 的 `status`  
  → 仅用于表述「测试点/用例/评审 Done」等**设计资产进度**，且须与飞书 Sprint 对得上。  
- 用户本周明确说过的事（如回归包整理 60%）→ 直接采用用户数字，勿臆造。

### 明确不读（现阶段）

- `docs/execution/**/run-log.md`、`execution-plan` 完成率  
- `bug-verify-log.md`  
- MeterSphere 执行率  

（数据不全时写入会造成虚假精确；以后若用户显式要求再开。）

## 工作流

1. 确认统计周与 `project_key`  
2. 拉飞书待办/已办 + 本周相关 Story/Bug；**同时**用 MQL 拉**下一 Sprint**（由当前 Sprint 结束日推算，如 `20260807` → `OBIS-20260810-20260821`）Story 列表；可选读 registry 对齐设计阶段  
3. 判定 Sprint 边界：写报日是否已到/超过本 Sprint 结束日与排期 `end_time`；跨边界则下周主写新 Sprint，旧 Sprint 最多作为「本周工作」收口  
4. 向用户确认缺口（进度%、待验收项、纯本地工作如回归整理）——**缺进度不要瞎填 %**  
5. 按「输出版式」起草三段  
6. 自检：标题三字不改；有协调才写协调，否则「暂无。」；**下周未误把已结束 Sprint 写成继续执行**；下周与本周动作阶段不重复粘贴  
7. 输出 Markdown；若用户要落盘，默认  
   `docs/sprints/{当前或主 sprint}/reports/weekly-{YYYYMMDD}-{YYYYMMDD}.md`  
   （日期为统计周起止）

## 写作规则

- 中文；简洁；可直接粘贴飞书  
- 不写密钥、账号密码、env 内容  
- 不写「根据某某文件分析」元叙事  
- 缺陷：可并入「本周工作」某包下的验收/阻塞一句，或放到「需要协调与帮助」；不要单独做成第四大段（除非用户要求）  
- 进度 %：有依据才写；多 Story 收尾可写包级进度，子项用状态词（待验收 / Done）

## 完成检查

- [ ] 仅三段标题：本周工作 / 下周计划 / 需要协调与帮助  
- [ ] 编号工作包 + `【标签】` 子项风格一致  
- [ ] 未引用 execution / bug-verify 半成品数据  
- [ ] 无进度依据处未编造百分比  
- [ ] 下周未在 Sprint/排期已结束后仍写「继续本 Sprint 测试执行」
- [ ] 已查询下一 Sprint（或用户确认无新 Sprint）
