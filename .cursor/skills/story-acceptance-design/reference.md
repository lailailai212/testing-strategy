# Reference — Story Acceptance Design

## Small / Large 自动判定

### Small（默认尝试）

- 1 个 Story / 1 个用户目标
- 预估 ≤ 8 条验收条目
- 1 个入口、1 条主路径
- 角色 ≤ 2，无复杂状态机

### Large（任一命中）

- 跨模块或多条主路径
- 预估 > 8 条 AC 或 > 10 个字段/规则
- 多角色权限矩阵
- 分期交付
- 需区分 AC 覆盖与 QA 扩展审计

输出时写清：`判定为 Large，因为 …`

## 变更类型（UI/UX | Logic | Hybrid）

与 Small/Large **正交**：Small/Large 管产出粒度；变更类型管**测什么、P0 密度偏向哪里**。

读需求后必判定一类；文档头写：`**变更类型**: …（判定依据一句话）`。Hybrid 须写清主/次，例如：`Hybrid（主 UI/UX，次 Logic：权限可见）`。

### 如何识别

| 类型 | 触发信号（示例） | 反信号（通常不是此类） |
|------|------------------|------------------------|
| **UI/UX** | 布局/间距/组件替换、文案改版、控件态（默认/hover/disabled/loading）、空态、交互反馈、Figma/截图主导；AC 多写「看到、展示、点击后出现」 | 正文大量「仅 1 次、计入、权限矩阵、状态流转」且无界面验收 |
| **Logic** | 业务规则、条件分支、状态机、配额/去重、权限能力、通知触达、数据落库/副作用；AC 多写「应/不应、仅…次、记在谁」 | 仅改文案/样式且无规则变化 |
| **Hybrid** | 既改界面又改规则（常见：新入口 + 新校验；展示条件依赖业务状态） | — |

用户明确说「偏 UI」或「偏逻辑」时，以用户指定为主类型，冲突点列入待确认。

### 与规则类型 A–D 的关系

| 层 | 作用 |
|----|------|
| **变更类型** | 设计偏置：P0 测什么、少测什么 |
| **规则类型 A–D** | 安全网：命中则强制补漏测语义，**不因主类型是 UI/UX 而跳过** |

例：欢迎信**文案**改版 → 主类型 UI/UX，仍扫描 B；若触发/收件人未变，B 可标 N/A 并一句说明。配额规则改 → 主类型 Logic，跑 D；纯样式不进 P0。

### 各类型测试点侧重（强制偏置）

#### UI/UX（主）

| 必须覆盖 | 通常不进 P0（除非需求验收或影响可用性） |
|----------|------------------------------------------|
| 入口可达与导航路径 | 深层业务状态机矩阵 |
| 控件可见 / 隐藏 / 置灰 / 可选 | 无界面变化的纯数据副作用 |
| 文案、默认值展示、空态 / 加载态 / 错误提示展示 | 与本次改动无关的跨模块回归大网 |
| 关键交互：打开 → 操作 → 态变化（含取消/关闭） | — |
| 有 baseline/截图时：与约定视觉结果一致（或标待确认） | — |

Logic 类 TP 仅当「展示/可点依赖业务条件」时写，并标清依赖条件。

#### Logic（主）

| 必须覆盖 | 通常不进 P0 |
|----------|-------------|
| 主路径业务结果（成功/阻断） | 纯间距、配色、无文案变更的样式 |
| 规则矩阵：边界、负向、恢复（与拆分规则 + A–D 对齐） | 与规则无关的装饰性 UI |
| 权限能力 × 触达/归属（若涉及） | — |
| 受影响主路径的**相关回归**（点名模块，避免无边界全站回归） | — |
| Toast/跳转等反馈：仅保留能证明规则生效的最小可观察点 | — |

#### Hybrid

1. 声明主类型，P0 条数与用例比例跟主类型  
2. 次类型至少覆盖其强制清单中与本次改动相关的项，可多为 P1  
3. 禁止只写 UI 或只写规则一侧却宣称设计完成

### 设计自检（变更类型）

产出 `acceptance.md` 时在 `## 设计自检` 增加「变更类型」小节（见模板）；宣称完成前须勾选。

## 固定产出目录

| 类型 | 路径 |
|------|------|
| 验收 + 测试点 MD | `docs/sprints/{sprint}/features/{feature-slug}/acceptance.md` |
| Feature 元数据 | `docs/sprints/{sprint}/features/{feature-slug}/META.md` |
| 索引 | `docs/sprints/features-registry.json` |

- `{sprint}`：飞书 Sprint id（如 `OBIS-20260622-20260703`）
- `{feature-slug}`：小写英文连字符（如 `self-reg-001-05-domain-whitelist`）
- 目录不存在时自动创建；同路径覆盖更新；**禁止** `*-new.md`
- 模板：[docs/templates/test-points-template.md](../../../docs/templates/test-points-template.md)

## Story AC 输出形态

统一使用 `## Story AC` + 编号段落，**不用表格**。

Large 模式若飞书 Description 已含 **AC-01～AC-N**，Story AC 节**优先与飞书原文对齐**，每条保留 `（AC-0x）` 前缀，便于与开发 Story Comment 一致。

条与条之间空一行；P1 / 待确认项在编号后标注。

## 测试点拆分规则

1. **主路径**：每条 AC → 至少 1 个 P0 测试点
2. **字段规则**：每个必填/格式/范围 → 1 边界或负向（P1，标 `QA扩展`）
3. **权限（两维）**：
   - **能力**：谁能做操作（角色差异 → 1 条；P0 若阻断）
   - **触达/归属**：结果归谁、通知给谁、配额记谁——与「谁操作」解耦时**必须另写 TP**（见下方强制清单 B/C）
4. **反馈**：Toast / 跳转 / 留页 → 可合并入主路径或单独 TP
5. **负向 + 恢复**：
   - **负向**：失败不触发 / 不落库 / 不发信（创建、提交、签发、烧录等，标 `QA扩展`）
   - **恢复**：失败后再次成功时，行为与「干净首次成功」一致——**里程碑/去重类为 P0 独立 TP**，禁止停在「失败不生效」
6. **需求正文有、AC 未列**：保留测试点，来源列标 `需求描述`（如用户侧流程、邮件通知）

写完基础拆分后，必须再跑下一节「规则类型与强制清单」。

## 规则类型与强制清单

读需求后扫描是否命中下表；**命中任一类则清单项须落为独立 TP（或 Small 下独立 AC）**，不得只写在主路径括号/备注里。未命中的类型跳过。

### 如何识别

| 类型 | 触发关键词 / 信号（示例） |
|------|---------------------------|
| **A. 里程碑 / 去重事件** | 首次、仅 1 次、按 Tenant/Account 去重、里程碑、欢迎信、达成后通知 |
| **B. 异步通知** | 邮件、站内信、Webhook、短信；收件人、创建者、Admin |
| **C. 多角色可见 / 触达** | 仅注册者、Tenant Admin、邀请成员、运营开通、升级后不展示 |
| **D. 配额 / 用量归属** | 配额、用量、不计 Demo、记在谁头上 |

### A. 里程碑 / 去重事件（强制）

| # | 必须覆盖的语义 | 优先级建议 |
|---|----------------|------------|
| A1 | 首次**业务成功** → 触发 | P0 |
| A2 | 再次成功 → **不重发 / 不重复计数**（独立 TP 或场景表可直读，勿仅埋步骤末尾） | P0 |
| A3 | **业务失败** → 不触发，且**不占用**「首次」额度 | P0 |
| A4 | 失败后再成功 → 仍按首次成功触发，且仅 1 次（**恢复**，与 A3 成对） | P0 |
| A5 | 排除路径（Demo / 运营开通 / 升级后等）是否占用「首次」额度 | P0 |

### B. 异步通知（强制；常与 A 叠加）

| # | 必须覆盖的语义 | 优先级建议 |
|---|----------------|------------|
| B1 | 收件人集合（仅创建者？含 Admin？评论已确认的以评论为准） | P0 |
| B2 | **触发者 ≠ 收件人**：非创建者/非约定角色操作时，仍只发给约定收件人；操作者本人不收 | P0 |
| B3 | **业务失败**不发 vs **投递/通道失败**重试——**分两条线**，禁止共用一个「失败」TP | P0 |
| B4 | 变量/`{name}` 等取约定主体（通常为创建者），不随操作者变化 | P1～P0 |

### C. 多角色可见 / 触达（强制）

- 至少给出最小矩阵思维：`角色 × 租户/签约/升级状态` 的展示或触达分叉
- 「创建者操作时他人不可见/不收」**不能替代**「非创建者操作时仍只触达创建者」
- 可见性样例参考：`docs/sprints/_examples/welcome-account-scenario-matrix.md`

### D. 配额 / 用量归属（命中时）

- 何种资源计入 / 不计入；操作者换人时记在谁头上；排除项是否占额度——各至少 1 条 TP

### 设计自检（命中 A/B/C/D 时产出文档须勾选）

输出到测试点 MD 的 `## 设计自检`（或模板同名节）。清单项与上表对应；全部勾选后方可宣称设计完成。反面教训见 [examples.md](examples.md)「示例 D」。

## TP-ID 命名

| 段 | 含义 | 示例 |
|----|------|------|
| 前缀 | `TP` | 固定 |
| 模块缩写 | 页面/模块 | `ACCT`、`REG`、`MAIL` |
| 子区缩写 | 可选 | `APP`、`ACT`、`PERM` |
| 序号 | 两位数字 | `01` |

示例：`TP-ACCT-APP-01`、`TP-REG-POST-02`

## 优先级（P0 / P1 / P2 / P3）

| 级别 | 含义 |
|------|------|
| P0 | 主流程、阻断性规则；冒烟 / 发版前必跑 |
| P1 | 边界、重要负向；回归必关注 |
| P2 | 低频组合、待确认场景 |
| P3 | 体验细节、极低频边缘 |

## AC 追溯规则

### 测试点 → Story AC（「来源」列）

- 覆盖 Story AC 时填 **AC 编号**：`AC-01`；多条用逗号分隔
- 无对应 AC 时填 `需求描述` 或 `QA扩展`

### AC → 测试点（追溯矩阵）

每个 `## AC ↔ 测试点追溯矩阵` 表格行：

| Story AC | 覆盖测试点 | 覆盖状态 |
|----------|------------|----------|

- 覆盖状态：✅ 至少 1 条 P0；⚠️ 仅 P1；❌ 未覆盖（不应出现，需补 TP）
- 矩阵末尾声明：**AC-01～AC-0N 均已至少 1 条 P0 测试点覆盖**

### Large 模式职责分层

| 层 | 读者 | 粒度 | 产出 |
|----|------|------|------|
| Story AC | 开发 | 粗、可勾选 | `## Story AC` |
| 测试点 | QA | 细、可执行 | `## 测试点` + 追溯矩阵 |

Story AC 不可粗到不可测（避免「功能正常」）。

## 待确认（Open Questions）触发词

- 刷新、成功、失败的具体表现未定义
- 登录后 redirect vs 手动导航
- 权限：隐藏按钮 vs 禁用 vs 提交后 403
- 列表 filter/分页下创建后的行为
- 错误文案未给出
- 飞书 AC 与需求正文不一致（以最新评论为准，差异写入待确认）
- 「首次」以业务成功还是以首次尝试计；失败是否占额度（未写清则列入待确认并默认按「首次成功」设计 A3/A4）
- 通知收件人：创建者 vs Admin vs 操作者（未写清则列入待确认）
- 业务失败与投递失败的可构造/可观测方式
