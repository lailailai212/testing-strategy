## 文档结构模板

```markdown
# {需求中文名} 功能测试用例

> 来源：`docs/sprints/{sprint}/features/{feature-slug}/acceptance.md`（推荐；含 TP-ID）或 tree JSON / XMind（叶子无 TP-ID，须回查 MD）  
> 需求：{Story / 功能全称}  
> 变更类型：UI/UX | Logic | Hybrid（与 acceptance 对齐；Hybrid 写主/次）  
> 用例数：{N}（P0 × a，P1 × b，…）；类型分布：UI × u，Functional × f，E2E × e  
> 入口规则：{页面 → 区域 → 按钮 → 弹窗；无则省略本行}  
> 产品规则：{字段/默认值/权限等差异；无则省略本行}  
> 用例名称格式：`【{页面模块}】【{类型}】{子功能} - {描述}`（`{类型}` = `UI` | `Functional` | `E2E`；说明模块归属约定）

| --- | --- | --- | --- | --- | --- | --- | --- |
| … | … | … | … | … | … | … | … |
```

## 备注列（来源，必填）

每条用例必须填写「备注」，表明来源。

若是来源于需求 AC，则标为：

```text
来源 AC-01: Welcome 邮件在自注册 Tenant 创建成功后发送，按 Tenant 仅 1 次
```

| 来源类型 | 写法示例 |
|----------|----------|
| 需求 AC | `来源 AC-01: Welcome 邮件在自注册 Tenant 创建成功后发送，按 Tenant 仅 1 次` |
| 多条 AC | `来源 AC-01: …<br>来源 AC-04: …` |
| 需求描述 | `来源 需求描述: Matter module 首次烧录同时收到 DAC 与烧录两封邮件` |
| QA 扩展 | `来源 QA扩展: 真实 DAC 签发失败时不发送首次 DAC 邮件` |

规则：

- AC 编号后必须跟 **Story / 飞书验收标准原文**，禁止只写 `AC-01` 或自行改写
- 优先引用本条用例主命中的 AC；同场景覆盖多条 AC 时全部列出
- 无对应 AC 时按测试点「来源」列选用 `需求描述` / `QA扩展`

## 用例名称范式

### 格式

```text
【{页面模块}】【{类型}】{子功能} - {一句话描述}
```

### 用例类型（`{类型}`）

名称中的 `{类型}` **必须**为以下三者之一，不得写笼统的 `【功能】`：

| 类型 tag | 含义 | 典型场景 |
|----------|------|----------|
| `UI` | 界面与交互态 | 控件可见/隐藏、按钮置灰、错误文案展示、弹窗按钮布局 |
| `Functional` | 功能与业务规则 | 字段校验、配额计数规则、边界值、失焦/提交阻断 |
| `E2E` | 端到端主路径 | 从列表入口经多步向导到创建成功/阻断的完整旅程 |

分配原则：

- 一条用例**只标一种**类型，按主要测试意图选择
- 展示与规则同时涉及时：侧重**业务规则** → `Functional`；侧重**控件展示** → `UI`
- 需跨多步页面或完整创建流程验证 → `E2E`
- Story **变更类型**决定包内比例（见下节）；单条 tag 仍按该条意图选择
- 与 MeterSphere「用例类型」列可独立；名称中的类型 tag 供筛选与自动化分层

## 变更类型与展开偏置

读取 `acceptance.md` 头的 `**变更类型**`；缺失时按 TP/AC 语义自判并写入用例 MD 头。

| Story 变更类型 | 用例比例建议 | 步骤/校验偏置 |
|----------------|--------------|---------------|
| **UI/UX** | 多数 `【UI】`；少量 `E2E` 仅覆盖关键入口旅程 | 细步骤、界面断言；禁止为凑覆盖写深规则矩阵用例 |
| **Logic** | 多数 `【Functional】`/`【E2E】`；`【UI】` 仅阻断态/关键文案 | 业务步骤与结果断言；禁止逐步逛界面而无业务结论 |
| **Hybrid** | 跟主类型；次类型单独成条（可 P1） | 主场景按主类型颗粒度写；次类型不混进无关步骤 |

与上游关系：变更类型来自 `story-acceptance-design`；规则类型 A–D 仍约束「须有哪些场景」，不改变上表颗粒度。

## UI vs Functional 步骤与校验

**核心**：同属「可执行用例」，但 `【UI】` 与 `【Functional】`/`【E2E】` 的**步骤拆多细、预期验什么**不同。禁止用同一套「打开→填表→提交→看 Toast」模板套所有用例。

### 步骤颗粒度

| | `【UI】` | `【Functional】` | `【E2E】` |
|--|----------|------------------|-----------|
| 典型步数 | 3～7（交互态多时可接近 10） | 3～6 | 5～10 |
| 步骤写什么 | 定位到**具体控件/区域**；每次交互可占一步（展开下拉、切换 Tab、清空输入、点取消） | **业务动作**为主；连续填写多个必填项可合并为一步（预期只关心能否继续/提交结果） | 跨页/多步向导的关键站：入口 → 中间必要页 → 终态 |
| 前置条件 | 账号与页面可达即可；少造复杂业务数据 | 写清角色、Tenant 类型、配额/历史数据等**规则前置** | 同 Functional，并写清跨页起点数据 |
| 拆步信号 | 「看到态变化」需要独立操作才能触发 → 可拆步 | 「另一套规则前置/另一业务时刻」→ **拆条**而非拆步 | 旅程过长或互斥终态 → 拆条 |

### 校验点（预期结果）

| | `【UI】` 预期应写 | `【Functional】`/`【E2E】` 预期应写 |
|--|-------------------|-------------------------------------|
| 主断言 | 可见/隐藏、启用/置灰、文案、选项集合、布局与按钮组合、空态/加载态、即时校验提示展示 | 提交成功或阻断、资源计数 ±1、列表/详情字段值、邮件/通知触达与否、权限允许/拒绝后的业务后果 |
| 可附带 | 同一步内并列多个态（分号） | 证明规则生效的最小反馈（一条 Toast/跳转）；**不要**附带整页 UI 巡检清单 |
| 不要写 | 深层「仅 1 次 / 记在谁头上」等规则结论（应另开 Functional 条）；**`COPY-NN` /「文案符合 COPY-xx」**（须写界面可见原文） | 「间距好看」「风格一致」等无验收标准的体验句；与本次规则无关的控件外观；**文案编号代号**（同左，写原文） |

#### 文案断言（强制）

用例给人执行：名称 / 前置 / 步骤 / 预期中**禁止**依赖 `COPY-01` 等编号。

```text
❌ Toast 为 COPY-02；文案符合 COPY-01
✅ Toast 为「SE Profile 已锁定」（英文：SE Profile locked.）
✅ 确认框文案为「锁定后该 SE Profile 禁止建立新引用，已有引用继续有效。可随时解锁恢复。确认锁定？」；含确认 / 取消
```

备注列引用飞书 AC 原文时可保留原文中的 COPY-NN；可执行列仍须写清可见文案。

### 正例 / 反例（对照）

**场景**：Tag 空值时 Add 不可用（UI）

```text
✅【UI】
步骤：[1] 打开 Tag 新增入口 [2] 将名称清空或不填 [3] 观察 Add
预期：[2] 输入框为空或校验提示可见 [3] Add 置灰不可点

❌ 写成 Functional 深路径
步骤：造数 → 多次提交 → 断言配额与邮件…（与空值置灰无关）
```

**场景**：二次成功不重复发信（Functional）

```text
✅【Functional】
前置：Tenant 已成功触发过首次邮件
步骤：[1] 再次完成同一业务成功操作 [2] 检查创建者收件箱/通知
预期：[1] 业务成功 [2] 不产生第二封对应邮件

❌ 写成 UI 细逛
步骤：逐步点开各 Tab、核对文案与按钮布局，却不验证「是否多发一封」
```

### 同场景 UI + 规则

| 情况 | 做法 |
|------|------|
| 同一次操作后，控件态与业务结果都要验，且步骤 ≤ 10 | 可同条；名称按**主意图**选型；预期内分号并列，业务结论写在前或单独编号步 |
| 规则矩阵（角色×状态、去重、恢复） | **必须** Functional/E2E 分条；UI 态不进这些条的主断言 |
| Story 主类型 UI/UX，但有一条强规则 AC | 单独 Functional 条覆盖该 AC，不抬高整包为 Logic 写法 |

## 页面模块 slug 约定

**由所属模块路径推导**，取平台根（如 `/Cloud`）之后的层级，用连字符拼接为单一 slug：
| 所属模块 | 名称前缀示例 |
|----------|--------------|
| `/Cloud/Product/Assets` | `【Product-Assets】【Functional】` |
| `/Cloud/Product/Version` | `【Product-Version】【E2E】` |
| `/Cloud/KMS/Key List` | `【KMS-Key-List】【E2E】` |
| `/Cloud/SEMS/SE-Profile-Detail` | `【SEMS-SE-Profile-Detail】【E2E】` |

规则：

- slug 用**英文连字符**；模块名含空格时保留单词间连字符（如 Product Asset 模块在 MS 中为 Assets → `Product-Assets`）
- **仅一个** `【{模块 slug}】` 前缀，禁止 `【Product】【Version】【UI】` 等嵌套写法
- `{子功能}` 对齐 XMind 二级分支（如 Assign Security Key、Asset 列表）
- `{一句话描述}` 来自测试点叶子描述，可略作润色但不可改义
- **禁止**在用例名称中写 TP-ID

### 命名示例

```text
【Product-Assets】【Functional】Assign Security Key - Tag 下拉单选已有 Tag
【Product-Assets】【UI】Tag 新增 - 空值时 Add 置灰
【Product-Version】【E2E】Certificate Tag 与 Asset 一致
【KMS-Key-List】【E2E】密钥数量配额 - 已有 5 个密钥触达上限阻断
【KMS-Create-Key】【UI】密钥有效期 - Unlimited 选项不可见
```

## 所属模块路径

- 以 `/` 开头，反映**产品导航层级**，非代码路径
- Product 模块下的 Version、Product Detail、Product Asset **均挂在 `/Product/` 下**
- 最后一级对齐 XMind 子功能名（可与 UI 文案一致）

```text
/Product/Product Asset/Assign Certificate
/Product/Product Asset/Tag 新增与删除（Key/Certificate 共用）
/Product/Version 详情页
/Product/产品详情页
```

### MeterSphere 模块（禁止自行推理）

**所属模块必须来自 MeterSphere 已有模块树**，不得根据 XMind/页面结构自行拼路径。

生成或更新用例前，需具备以下数据之一（推荐同时提供 ① + ②）：

| 优先级 | 你提供的内容 | 文件建议路径 | 用途 |
|--------|--------------|--------------|------|
| ① 必须 | **合法模块路径清单**（MeterSphere 里真实存在的全路径） | `docs/modules/{project}-modules.json`（当前：`metersphere-modules.json`） | 校验 `module_path` 合法，导入不失败 |
| ② 必须 | **TP-ID → 模块路径映射** | `docs/sprints/.../features/{slug}/testcases/module-mapping.json` 或 `.csv` | 自动填「所属模块」列 |
| ③ 可选 | MeterSphere 模块树导出（截图/Excel/JSON） | 任意，作人工核对 | 确认路径拼写 |
| ④ 可选 | XMind 二级分支名 → 模块路径 | 合并在 mapping 的 `xmind_branch` 列 | 尚无 TP-ID 时先按分支映射 |

模板见：

- [metersphere-module-mapping.example.json](../../../docs/templates/metersphere-module-mapping.example.json)
- [metersphere-module-mapping.example.csv](../../../docs/templates/metersphere-module-mapping.example.csv)

**映射规则**：

- 每个 TP-ID 对应**一条** `module_path`（对应该 Story 在 MeterSphere 中的挂载位置）；合并用例取所覆盖 TP 的共同路径，路径不一致时拆条或标待确认
- 同一 XMind 分支下多条 TP（TP-PA-KEY-01/02）通常共用同一路径，可合并进同一用例
- 路径必须与 MeterSphere **完全一致**（`/Product/Product Asset/Keys` ≠ `/Product/Product asset/Keys`）
- 映射表无命中 → 标记「待确认」，**不要**猜填

**你从 MeterSphere 侧需要导出的信息**（任选一种给我即可）：

1. **模块树全路径列表**（最理想）：每行一个路径，如 `/Product/Product Asset/Keys`
2. **模块树截图 + 手工整理 CSV**（见 example.csv）
3. **MeterSphere 导出的用例 Excel**：我从已有用例的「所属模块」列反推合法路径（仅当有同产品历史用例时可靠）

**最小 CSV 示例**（你只需填两列也能用）：

## 标签列

**只填可读业务标签**，不写序号类编码。

```text
{Feature 或 Story 短名}
```

示例：

- ✅ `CreateModule与AddAssetType权限`
- ✅ `Product Asset Tag`
- ✅ `Transactional Email`
- ❌ `CreateModule与AddAssetType权限;TP-MOD-POS-01;TP-MOD-POS-03;AC-01;AC-05`
- ❌ 单独或夹带 `TP-*`、`AC-0x` 等不可阅读序号

- 不写 P0/P1（已独立为用例等级列）
- TP / AC 追溯写在「备注」列与文档头「场景与 TP 覆盖」表，**不要**塞进标签

## 用例等级（P0–P3）

| 级别 | 适用 |
|------|------|
| **P0** | 主流程、阻断性规则、核心 Assign/提交、跨页主路径一致性 |
| **P1** | 边界（空值置灰）、重要负向（重复名校验）、历史数据展示 |
| **P2** | 低频组合、待确认场景、非阻断细节 |
| **P3** | 极低频边缘、体验细节 |

分配原则：

- 测试点表若全标 P0，展开时仍按**实际场景**重评（历史数据、纯边界常为 P1）
- 一条用例在**同一场景内**合并 P0+P1 校验点时，以**最高阻断级别**定等级
- 不同用户场景即使都是 P0，也**分条**编写，不因「都想冒烟」而合成一条超长用例

## 前置条件

- 编号 `1. 2. 3.`
- 包含：角色/权限、页面位置、测试数据状态
- 写**完整入口**（不只写「已打开弹窗」，而写如何打开）
- 依赖数据说明准备方式（如「先通过 Certifications **Assign Certificate** Add 创建 Tag」）
- **造数 / 登录 / 切租户等准备动作优先写前置条件**，避免挤占步骤名额（步骤上限 10）

## 步骤描述与预期结果

### 编号格式

```text
[1] 第一步操作
[2] 第二步操作
```

Markdown 表格单元格：

```text
[1] 在 Product Asset 页 **Keys** 区域点击 **Assign Key**<br>[2] 展开 Tag 下拉
```

### 对齐规则

- 预期 `[n]` 对应步骤 `[n]` 的可观察结果
- 步骤只写操作，预期只写结果，避免混写
- UI 按钮/区域名与产品一致，关键操作加 **粗体**
- **步骤保持清晰与逻辑性**：按用户真实操作顺序编排；`【UI】` 允许「一步一交互」，`【Functional】` 允许「一步一业务动作（可含连续填写）」
- **单条用例步骤数 ≤ 10**（`[1]`～`[10]`）；超出则：① 准备动作下沉前置条件；② 一步多断言合并预期；③ 仍超或已跨场景则拆条
- 单步可观察多个结果时，写在同一 `[n]` 预期内（分号并列），不为每个断言单独占一步
- 断言内容必须与用例类型匹配（见「UI vs Functional 步骤与校验」）

### 入口写法（通用）

步骤中必须写清：**页面 → 区域/Section → 按钮 → 弹窗/结果**

反例：`点击 Assign Security Key`  
正例：`在 Product Asset 页 **Keys** 区域点击 **Assign Key**，打开 Assign Security Key 弹窗`

## 从测试点展开（一场景一条 + 场景内多校验）

用例每个用例其实都是几条用户场景，尽量保证用一条用例覆盖一个场景，但可以校验更多的测试点。测试用例步骤需要依旧保持步骤的清晰和逻辑性。同时用例最长步骤不要超过 10 步。

| 测试点叶子 | 展开策略 |
|------------|----------|
| 同一用户场景内多条 TP | **合并**为一条用例；场景内尽量多校验；标签列只写可读 Feature 名（勿塞 TP-ID/AC） |
| 不同业务时刻 / 独立场景 | **分条**（如 Welcome、首次 DAC、首次烧录各一条） |
| `TP-XX-01 \| A；B；C` | 同场景内多步/多断言；B/C 属另一场景或互斥时拆条 |
| 控件 + 规则 | 主意图选型：偏展示 → `【UI】`；偏规则 → `【Functional】`；同场景可同条但预期分清态 vs 业务结果，规则矩阵仍须分条 |
| 必填负向 + 正向 | Functional：同表单连续编号；UI：单独验置灰/提示展示；步骤将超 10 时再拆 |
| 列表一致 | Logic：可与同场景提交合并断言列值；纯展示改版：独立 `【UI】` |
| 跨页一致 | 仅当属于**同一用户目标场景**时同条；否则分条 |
| 历史数据 / 独立负向 / 不同角色 | **拆分**；勿硬塞进无关场景 |
| Demo vs 真实、运营开通 vs 自注册等互斥前置 | **必须拆分** |
| 业务失败后再成功（恢复发信/计数） | **必须拆分**；勿并进「仅失败不发」负向条后停手 |
| 非创建者触发、验收件人/归属 | **必须拆分**；勿用「创建者操作时他人不收」替代 |
| 邮件/消息**通道重试** | 与业务失败不发信**分条** |

## 产品规则 blockquote

用户在对话或 PRD 中澄清的差异规则，写入文档头，并同步到相关用例步骤/预期：

- 入口路径（哪个 Section 的哪个按钮）
- 字段默认值差异（如仅 Cert 有系统默认 Tag）
- 模块归属（Version 属于 Product）

勿将仅适用于单个 Story 的规则写进 skill 正文；写在具体 MD 的 blockquote 中。

## 质量检查清单

- [ ] 文档头已声明**变更类型**，且 `【UI】/【Functional】/【E2E】` 比例与之匹配
- [ ] `【UI】` 用例步骤细到控件交互，预期以界面态/文案为主
- [ ] `【Functional】/【E2E】` 用例步骤以业务动作为主，预期以业务结果/副作用为主（无整页 UI 巡检）
- [ ] 未用 UI 用例承担规则矩阵，也未用 Functional 用例只逛界面不验业务结论
- [ ] 每条用例只覆盖**一个**用户场景（未把多个独立业务时刻硬塞进一条）
- [ ] 同一场景内已尽量合并可连续校验的 TP，避免无必要的「一点一案」
- [ ] 每条 TP-ID 至少被 1 条用例覆盖
- [ ] 步骤清晰、因果连贯；步骤数 ≤ 10；准备动作已尽量下沉前置条件
- [ ] 用例名称符合 `【模块】【UI|Functional|E2E】子功能 - 描述`，无笼统 `【功能】`
- [ ] 所属模块路径含正确 Product 层级（或已标待确认）
- [ ] 用例等级非全 P0，且与场景匹配（同场景内取最高阻断级别）
- [ ] 步骤含完整入口路径，贴合真实操作顺序
- [ ] 步骤与预期编号对齐；一步多结果写在同一预期编号内
- [ ] 备注列已标明来源（AC 含原文；非 AC 标需求描述/QA扩展）
- [ ] 标签列仅为可读业务名，无 TP-ID / AC-0x 等序号类编码
- [ ] 产出路径为 `docs/sprints/{sprint}/features/{feature-slug}/testcases/{feature-slug}.md`
- [ ] 文档头统计用例数与等级分布正确
- [ ] 若存在「仅 1 次 / 首次 / 仅发给 XX」：场景表或用例标题能直读二次成功、失败恢复、操作者换人；未把关键断言只埋在步骤末尾
- [ ] 业务失败路径与投递/通道失败重试已分条（若测试点含两类）

## 待确认处理

PRD / baseline 未定义时：

- 步骤/预期不写死歧义文案，用「（待确认：…）」
- 在回复用户时列出 Open Questions
- 不阻塞其他已明确用例的生成
